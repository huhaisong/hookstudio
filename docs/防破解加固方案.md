## 0. 先说实话：Python 程序藏不住源码

这一节不能跳过，否则后面所有投入都可能白费。

你现在这套打包（PyInstaller onedir → 7z → 单文件安装器）的保护强度，本质是：

- `app/*.py`（49 个模块）被编译成 `.pyc` 塞进 PYZ。`.pyc` 有公开工具可反编译——但**修正（2026-11-22）**：Python 3.13 目前**没有成熟反编译器**（pycdc 稳到 3.12，uncompyle6/decompyle3 停在 3.8），实际门槛比"几分钟还原"高一档。但反汇编 + AI 拼装仍能还原逻辑结构，**所以混淆不能省**——这只是抬门槛，不是让源码消失。
- `web/`（含 323 KB 的 `app.js`）、`prompts/`（10 份提示词）是**原样明文拷贝**进安装包的，解压即读，零门槛。
- 安装器本身只是个自解压壳（7z + PyInstaller onefile），**加壳不等于加密**：任何人都能把它解开，拿到里面的 onedir 目录。

所以：

> **能做到的是「把门槛从中学生抬到专业人员 + 几小时」，做不到「让人看不到源码」。**
> 任何声称 100% 防破解的方案（尤其是对 Python）都是卖拐的。

真正保护商业利益的不是源码，是你已经建好的**服务端那把锁**：Key 代理、账号额度、版本号闸都在 `api.hookstudio.cn`，本机 `llm_key`/`ds_key` 留空时，破解客户端也调不动 AI。**这把锁比任何混淆都值钱，先别动它。**

## 2. 三档方案对比

## 3. 推荐组合：A 档 + 提示词内置 + 安装器 exe

按你的三个选择：只出方案（本文件）、提示词藏起来、交付安装器。落地顺序如下。**每一步都标了改动点和坑，动手时逐一核对。**

### 3.1 提示词：从"磁盘明文"改为"内置密文"

这是你特别要求的，也是最值钱的一步。四条路径按推荐度排：

1. **（推荐）内置进混淆后的 Python 模块**
   把 10 份 `prompts/*.txt` 的内容作为字符串常量写进一个新模块 `app/_builtin_prompts.py`，用 pyarmor 一起混淆。`app/analyze.py:50 _default_prompt()` 改成优先从这个常量表取，找不到再退回磁盘（开发期由 `HOOK_DEV_PROMPTS=1` 开关控制）。
   - 好处：改动集中、不引入新的解密依赖、和 pyarmor 混用天然。
   - 坑：字符串常量在混淆后仍可能从内存里 dump 出来——**这是"提高门槛"不是"消失"**。
   - **⚠️ 致命细节（2026-11-22 用户核对，务必按原字节写入）**：常量表里的 10 份内容必须**逐字节照抄源文件**——不要重新排版、不要动空行、不要改换行符（CRLF/LF）、不要美化缩进。`_default_prompt()` 现在是 `f.read().strip()`（analyze.py:54-55），`_split_fixed()`（134-143）按标记行做 `ln.strip() == mark` 的精确匹配。**技术归因修正**：当前 `FIXED_TAIL_MARKS = {}` 是空表，`_split_fixed` 对所有文件直接 `return text, ""`，所以此刻"锚点匹配失败"并不会发生；但一旦将来恢复固定尾巴（代码注释里明确留了恢复路径），任何字节改动都会让锚点对不上、固定尾巴被当成普通内容拼进请求，整条生成链路解析全崩。**按原字节写入是零成本的对冲，别偷懒重新排版**——这是最典型的"打包成功、跑起来全错"。
   - **写常量表的正确姿势**：用脚本读源文件二进制→`repr()` 或 JSON 转义生成字面量，别手工复制粘贴（中文 + CRLF 手工搬必出错）。写入后逐一 `len()` 比对原文件字节数，并跑一次 `_default_prompt(name) == 原文件.strip()` 的断言。

2. **（次选）AES 加密的单个资源文件 + 运行时解密**
   10 份提示词合并加密成一个 `prompts.bin`，密钥写死在混淆后的代码里。
   - 好处：安装包里连可读文本都没有。
   - 坑：密钥在客户端，专业人员照样能抠出来；多一层解密失败风险。

3. **（不推荐）服务端下发**
   启动时带设备令牌从 `api.hookstudio.cn` 拉提示词。最彻底，但要改服务端、断网不可用，且和"只有 Key 代理/账号/版本闸"的现状冲突。

4. **（兜底）物理删除磁盘 prompts**
   只要走 1 或 2，`build.bat:46` 的 `robocopy prompts ...` 就必须删掉，产物里不能留 `prompts/`。

**必须同步处理的连锁点（漏一个就白藏）：**

- `app/main.py:1458-1461` `GET /api/prompts/{key}` → **改 404**（第一批就做，全项目第一优先、与打包无关）。理由：它表面只返回"可编辑段"，但 `FIXED_TAIL_MARKS={}` 空表使 `_split_fixed` 对它无效，返回近乎全文；10 个 key 可枚举。零风险——`web/app.js:4101 PROMPT_EDIT_ON=false` 前端不发这个 GET，改 404 不破界面。这是成本最低、收益最高的一步，**不要等到打包阶段**。
- `app/main.py:1431-1442` `_PROMPTS` 表 → 保留（路由埋点要用），但键名不再对应磁盘文件。
- `app/analyze.py:42/185/200` 自定义提示词的读写 → 既然编辑已关，`data/prompts_custom/` 不会有人写；保留兼容但确认 `data/` 不进包（`build.bat` 已经只建空目录，OK）。
- `app/buildstamp.py:33-35` `_ROOTS` → `prompts` 目录不在包里后，`os.walk` 一个不存在的目录只会返回空、不报错，但指纹会变。改为把内置提示词模块纳入指纹（直接算 `app/` 目录即可，因为它已经含在内）。
- `app/core.py:29 PROMPTS` 路径常量 → 保留，别的地方还在引用；只是不再有真实文件。

### 3.2 Python 代码混淆（pyarmor）—— 先验两条，过不了就换 Cython

**⚠️ 全量混淆之前，先做一个单模块小样验证。两条任一不过，直接退 Cython，不要在 pyarmor 上耗。**

> **2026-11-22 实测更新（重要，修正下面的错误断言）**：本机装了 pyarmor 9.3.0（trial）实测：
> - **先验②的技术断言写错了**：pyarmor 官方文档明确——混淆产物**不绑定构建机、目标机不需要装 pyarmor 或验证 license**，"试用版打的包客户机起不来"是错的。trial 产物技术上能脱离构建机运行（已实测：单模块混淆产物换目录 import 正常）。
> - **真正的阻塞是 trial 的大脚本限制**：trial 能混淆 ≤41KB 的文件（如 `_builtin_prompts.py` 41KB、`admin.py` 13KB 均成功），但 `analyze.py`(101KB)、`main.py`(148KB)、`render.py`(152KB) 这些核心模块直接报 `ERROR out of license`。不是文件数（8 个文件的小样全过）、不是纯行数（3000 行注释能过）、不是函数数（200 个函数能过）——是代码对象规模触发的 big script 限制。`--obf-code 0` 也绕不过。
> - **结论**：trial 版混淆不了本项目最值钱的业务逻辑模块。"用 trial 跑通全链"这条路在 pyarmor 上走不通——除非买 license（Basic 解锁大脚本，一次性收费），或改走 Cython（但本机无 C++ 编译器，见第 8 节）。**这是需要在花钱/装工具链前拍板的点。**
> - 文档 Q&A："销售额未超过 license 费 100 倍前可用 trial"（中文页另写 30x，以官方 EULA 为准），但无论哪个口径，**Big Script 文件大小限制是硬卡**，trial 都绕不过。

**✅ 最终采用：Cython 编译核心模块为 .pyd 机器码（2026-11-22 实测全流程跑通）**

pyarmor trial 卡死核心大模块后，改走 Cython + zig（纯 pip 安装、免费、无需买证书、无需管理员权限）：

- `pip install Cython ziglang`：Cython 3.3.1 + zig 0.17.1，zig 自带 clang 兼容的 C 编译器（`zig cc`），绕开本机没有 cl/gcc 的问题。
- `build_cython.py`：把 12 个核心纯计算模块（analyze/shots/render/retime/proof/batch/transcribe/names/span_split/audiofp/bgmlib/reuse）编成 `.pyd`。
- **关键坑（已解决）**：Windows 下 zig cc 链接必须显式带 `python313.lib`（import lib），否则 `undefined symbol: PyModuleDef_Init` 等一堆 CPython 符号报错。lib 路径用 `sysconfig.get_config_var("LIBDIR")`（本机指向 WorkBuddy vendor 的 python/libs，与 3.13.14 同 ABI，两个 python313.dll 大小完全一致）。
- **实测通过**：`analyze.pyd`（988KB）能 import、能跑 `_default_prompt`（提示词逐字一致）、`_check_schema`，核心业务逻辑正常。
- 不编路由模块（main/admin/audit/auth/publishapi）：Cython 编译后函数签名丢失，FastAPI 靠签名反射注入参数会全崩。不编 core.py：基础设施、收益/风险不划算。
- 打包接入 `build_obfuscated.py`：临时把 `app/*.py` 换成 `.pyd` 再调 build.bat，`finally` 无条件还原源码（可逆）。
- 前端压缩：`build.bat` 里对产物副本的 app.js/publish.js 跑 terser `-c`（只 compress 不 mangle，实测 468KB→284KB、中文与 data-* 选择器全保留），源文件保持明文供开发调试。

**先验①：Python 3.13 兼容**
- 拿**单个模块**用 pyarmor 生成一次，把产物换到另一个目录（最好另一台机）import 跑通。
- 本机基础 Python 3.13.14——pyarmor 对 3.13 的支持版本相关，必须以实测为准，别信文档。

**先验②：分发授权**
- 试用版通常有分发限制（生成物绑定构建机 / 限制文件大小）。对外卖的产品**必须买 Basic/Pro**——拿试用版打出来的包在客户机上会直接起不来。这是"打包成功、客户机打不开"的典型事故。
- 先验时就要确认：生成物脱离构建机能否 import（这一条同时验了①和②）。

**两条都过，再全量：**
- 安装：`python -m pip install pyarmor`（基础 Python 3.13.14；本机未装）。
- 用法概要：`pyarmor gen` 处理 `app/` 生成混淆后的包，再让 PyInstaller 打混淆后的代码；不能直接对最终 exe 下手。
- **坑（必须实测）**：本项目 spec 里对 `faster_whisper`/`ctranslate2`/`onnxruntime` 用了 `collect_all`，它们带大量 `.pyd`/二进制，pyarmor 只管 `.py`。要确保混淆只作用于 `app/*.py`，别碰第三方包，也别碰 `run.py` 的启动入口逻辑。
- **坑**：混淆后如果模型调用报 `ModuleNotFoundError` 或转写出 0xC0000005，先怀疑隐藏导入丢失，回退到未混淆版本再定位，别在混淆态上 debug。

**退路：Cython（pyarmor 任一先验不过时启用）**
- 只编纯计算模块：`analyze / shots / render / nosub / proof / batch` 这类。
- **不编 `main.py` 等路由模块**——绕开 FastAPI 的签名反射（Cython 编译后函数签名丢失，FastAPI 靠签名注入参数会全崩）。
- 归档一份未混淆/未编译的构建脚本备用，失败时能一键回到可运行基线。

### 3.3 前端 JS 压缩（可选，低优先级）

- `web/app.js` 323 KB，可以用 terser 压缩 + 变量名混淆（`mangle`）。
- **收益有限**：前端逻辑本来就在浏览器里执行，用户永远能看到它"运行时"的样子；压缩只是让代码丑。
- **坑**：`app.js` 里有大量 DOM 选择器和字符串常量（含中文文案），激进 mangle 可能破坏 `data-*` 选择器或模板字符串。建议只做 `compress` 不做 `mangle`，或者干脆跳过这一步。

### 3.4 打包与安装器（沿用现有链路）

- 形态：**安装器 exe**，沿用 `build.bat → build_installer.py`，产出 `dist8/钩子工坊-0.1.x-安装.exe`。
- 版本号两处同步：`app/buildstamp.py:29 VERSION` 与 `deploy/proxy/release.json`。
- 打包前清 `dist/` 的 `data/`（带 Key 的开发机配置绝不能进包，见 `build_post.py` 和 `pack_zip.py` 的注释）。
- `runtime/Scripts/python.exe` 已坏：bat 在 cmd 里双击 historically 是通的；如果用脚本调，按项目惯例改用基础 python + `PYTHONPATH="runtime/Lib/site-packages;hookstudio;."`。
- 加壳/签名（C 档）**不建议叠加**：商业壳对 onnxruntime 的 `.pyd` 兼容差，很可能把转写弄崩，收益却是"源码照看"。

### 第二批 —— 混淆验证与全量

## 8. 补充评估：Nuitka 全量编译（2026-11-22）

用户问「能否用 Nuitka 全量编译」。结论：**能，但不推荐作为本项目的主方案**。逐条说明。

### 8.1 「全量编译」实际保护了什么（最容易误判的地方）

Nuitka 是把 Python 源码翻译成 C 再编译成机器码，和 PyInstaller「打 .pyc + 解释器」是两种东西。但对本项目：

| 产物 | Nuitka 做了什么 | 实际效果 |
|---|---|---|
| `app/*.py`（49 个模块） | 编译成机器码 | **真的强**：没有 `.pyc`，反编译门槛远高于混淆 |
| 第三方纯 Python 包 | `--follow-imports` 递归编译 | 收益为零（开源包本身公开） |
| `av`/`ctranslate2`/`onnxruntime` 的 `.pyd` | **原样复制，不编译** | 本来就是机器码，无变化 |
| `prompts/*.txt` | **完全不管** | 仍是明文，除非用商业版数据保护 |
| `web/*.js` | **完全不管** | 仍是明文，无解 |

所以「全量编译」**不等于「全部藏起来」**。它只把第一格从红变绿，其余三格一动不动。

### 8.2 三个硬障碍（本机实测）

1. **缺 C++ 编译器**：Nuitka 生成 C 代码后必须有本地编译器。`cl`/`gcc`/`clang` 全部不在 PATH，VS2019/2022、MinGW 都没装。且 Python 3.13 下 **MinGW64 明确不支持**，只能装 Visual Studio 2022 Build Tools（多 GB）或改用 `--zig`（小众、坑多）。
2. **runtime Python 是坏的**：`runtime/Scripts/python.exe` 因中文路径起不来；要用基础 Python 3.13.14 + `PYTHONPATH=runtime/Lib/site-packages` 跑 Nuitka。已确认关键 `.pyd` 都是 `cp313`，和基础解释器 ABI 一致——**这一条没问题**，但构建脚本要重写。
3. **编译耗时与调试**：49 个模块 + 依赖全量编译，Windows 上通常十几到几十分钟；编译后栈信息变差，而本项目大量排障依赖栈和行号（路由绑定、TDZ 那类坑），出问题定位成本显著上升。

### 8.3 兼容性：好消息与风险

- **好消息**：扫过 `app/`，没有 `eval`/`exec`/`importlib.import_module` 这类真正的高危动态导入，只有常规的 `re.compile` 和 `getattr`。这是 Nuitka 最容易编译的那类代码。
- **风险**：FastAPI 路由装饰器、uvicorn、faster_whisper 与 C 扩展的交互层仍需实测；不能只看编译通过，必须真跑一次完整链路（转写→编排→出片）。

### 8.4 授权：闭源商业项目要注意

Nuitka 标准版是 **AGPLv3**。官方立场是「编译你的代码不会让你的代码变成 AGPL」，但闭源分发仍有解释空间；真正想要 IP 保护三件套（常量混淆、数据文件加密、traceback 加密）必须买 **Nuitka Commercial（约 €250/年）**。你要的「藏提示词」恰好落在商业版卖点里——**标准版编译后，提示词字符串用 `strings` 命令就能从二进制里捞出来**。

### 8.5 结论与选择

| 你的真实痛点 | 更合适的方案 |
|---|---|
| 怕 `.pyc` 被反编译看到业务逻辑 | Nuitka 标准版确实最强，但要装 VS2022 + 重写构建链 + 慢编译 + 难调试 |
| **怕提示词被看到** | Nuitka 标准版无解；商业版要花钱；本文件 A 档的「内置 + 加密」更直接 |
| 怕前端逻辑被看到 | 所有方案都无解（前端必须在浏览器明文执行） |
| 综合性价比 | **仍推荐 A 档（pyarmor + 提示词内置加密）**：改动集中、不装 GB 级工具链、提示词和代码一起处理 |

若要走 Nuitka，建议只作为 A 档的替代分支：装 VS2022 Build Tools → 用基础 Python 跑 `python -m nuitka --standalone --follow-imports run.py` → 数据文件照样按本文件 3.1 节处理 → 实测全链路。**不建议为了「全量编译」四个字推翻已稳定的构建链。**

## 9. Nuitka 落地清单（选定它之后，逐项要做的事）

本节是「真要上 Nuitka 时」的执行清单。**未动手**。按依赖顺序排，1~4 是阻塞项，不做完编译必失败或运行必崩。

### 9.1 阻塞项（编译前必须解决）

**① 装 C++ 编译器（本机完全没有）**
- Python 3.13 下 MinGW64 官方不支持。二选一：
  - 装 Visual Studio 2022 Build Tools（含「使用 C++ 的桌面开发」），加 `--msvc=latest`；体积大但最稳。
  - 或装 zig（`pip install ziglang`），加 `--zig`，省空间但属于小众路径、坑多。
- 装完必须确认 `cl` 能在 VS Developer 环境里被找到，否则 Nuitka 报 "No C compiler"。

**② 解决「用哪个 Python 编译」——runtime 是坏的**
- `runtime/Scripts/python.exe` 因中文路径起不来；基础 Python 3.13.14 可用但**没装项目依赖**。
- 已实测可行的办法：用基础 Python + `PYTHONPATH` 指向 runtime 的 site-packages：
  ```
  set PYTHONPATH=D:\Users\eric\workbuddy\钩子工坊\hookstudio\runtime\Lib\site-packages
  python -m nuitka ...
  ```
  实测 `faster_whisper / av / onnxruntime / ctranslate2` 全部 import 成功，`cp313` ABI 一致。
- 注意 `--python-flag=isolated` / `no_site` 会让 Nuitka 忽略 PYTHONPATH，**别加这两个 flag**。

**③ ⚠️ 头号隐藏坑：`sys.frozen` 与 `web/` 路径**
- `app/core.py:20-31 _app_root()` 靠 `getattr(sys, "frozen", False)` 判断程序根目录：
  - PyInstaller 会设 `sys.frozen=True` → 根目录 = exe 所在目录（正确）。
  - **Nuitka 不设 `sys.frozen`**（实测机制不同），若不处理，`BASE` 会退回「源码目录」，编译后 `web/` `models/` `bin/` 全部找不到 → **编译成功但启动即报缺文件**。
- 解法：Nuitka 提供 `__compiled__` 内置变量。在 `core.py` 的 `_app_root()` 里把判断改成兼容两者：
  ```python
  frozen = getattr(sys, "frozen", False) or globals().get("__compiled__", False)
  ```
  （Nuitka 编译时 `__compiled__` 注入为 True；源码运行时不存在，故用 `globals().get`。**改完后必须编译产物实测一次**，确认取到的是 exe 目录。）
- 这是从 PyInstaller 迁 Nuitka **最容易漏、后果最严重**的一处。

**④ ⚠️ 二号隐藏坑：`uvicorn.run("app.main:app")` 字符串动态导入**
- `run.py:140` 用字符串 `"app.main:app"` 启动 uvicorn。Nuitka 的静态分析看不到字符串形式的模块名，可能**不把 `app.main` 编进去** → 运行时 uvicorn 加载失败。
- 解法：编译时显式包含：`--include-module=app.main`（配合 `--follow-imports`）。
- 同理，`app/` 下所有模块用 `--include-package=app` 或检查编译报告确认无遗漏。

### 9.2 编译命令（草拟，需按 9.1 改完后实测）

```
set PYTHONPATH=...\runtime\Lib\site-packages
python -m nuitka --mode=standalone --follow-imports ^
  --include-package=app --include-module=app.main ^
  --enable-plugin=anti-bloat ^
  --output-filename=钩子工坊.exe ^
  --windows-console-mode=console ^
  --msvc=latest ^
  run.py
```
- 输出是 `run.dist/`（standalone 目录），**不用 onefile**——和项目「onedir 绝不 onefile」的铁律一致，也才能接现有安装器链路。
- `--enable-plugin=anti-bloat` 可选，用于砍掉不需要的 stdlib 部分，减小体积。
