# 用户体系 · 埋点 · 封禁 —— 接入说明

> 适用版本：钩子工坊 0.1.0 起（2026-11-04 新增）
> 技术栈：FastAPI + SQLite（标准库）+ bcrypt + 原生 JS，**没有引入任何新的第三方依赖**
> 设计前提：**低侵入**——原有业务路由一行没改，全部能力靠「4 个新模块 + 1 个中间件 + 3 个新页面」挂上去。
> 产品定性（2026-11-04 用户明确）：**这是「需要登录」的工具，不提供免登录模式**；
> **AI Key 由服务端统一持有**，用户不填 Key，生成前向服务端申领一次性授权（见 §3.7）。

## 1. 表结构 SQL

三张表。**完整 DDL 在 `app/db.py` 的 `SCHEMA` 常量里**，启动时 `db.init()` 执行（`CREATE TABLE IF NOT EXISTS`，幂等）。

```sql
-- ── 用户 ────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT    NOT NULL COLLATE NOCASE UNIQUE,
    email         TEXT    COLLATE NOCASE,
    phone         TEXT,
    password_hash TEXT    NOT NULL,               -- bcrypt $2b$12$...
    display_name  TEXT    NOT NULL DEFAULT '',
    avatar        TEXT    NOT NULL DEFAULT '',
    role          TEXT    NOT NULL DEFAULT 'user'
                          CHECK (role IN ('user', 'admin')),
    status        TEXT    NOT NULL DEFAULT 'active'
                          CHECK (status IN ('active', 'banned')),
    ban_reason    TEXT    NOT NULL DEFAULT '',
    banned_at     TEXT,
    banned_by     INTEGER,
    -- 令牌代次：改密 / 封禁 / 解封 / 踢下线 / 改角色时 +1。
    -- JWT 里带签发时的值，跟库里对不上就立即失效（封禁即时生效的核心）。
    token_version INTEGER NOT NULL DEFAULT 0,
    fail_count    INTEGER NOT NULL DEFAULT 0,     -- 连续登录失败次数
    locked_until  TEXT,                           -- 锁定到这个时间点
    must_change_pwd INTEGER NOT NULL DEFAULT 0,   -- 初始密码/被重置后置 1
    last_login_at TEXT,
    last_login_ip TEXT    NOT NULL DEFAULT '',
    created_at    TEXT    NOT NULL,               -- UTC ISO，如 2026-11-04T10:00:00+00:00
    updated_at    TEXT    NOT NULL
);

-- ── 刷新令牌（服务端可撤销、可轮换、可查设备）────────────────────────────
CREATE TABLE IF NOT EXISTS refresh_tokens (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id        INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash     TEXT    NOT NULL UNIQUE,       -- sha256(令牌)，不存明文
    issued_at      TEXT    NOT NULL,
    expires_at     TEXT    NOT NULL,
    revoked_at     TEXT,
    revoked_reason TEXT    NOT NULL DEFAULT '',   -- logout / rotated / banned / kicked / pwd-reset
    ip             TEXT    NOT NULL DEFAULT '',
    ua             TEXT    NOT NULL DEFAULT ''
);

-- ── 操作日志（埋点）───────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS audit_logs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at  TEXT    NOT NULL,
    user_id     INTEGER,                          -- 未登录请求为 NULL
    username    TEXT    NOT NULL DEFAULT '',
    role        TEXT    NOT NULL DEFAULT '',
    method      TEXT    NOT NULL DEFAULT '',
    path        TEXT    NOT NULL DEFAULT '',      -- 实际路径 /api/projects/abc123/plan
    route       TEXT    NOT NULL DEFAULT '',      -- 归一化 /api/projects/{id}/plan（统计用）
    query       TEXT    NOT NULL DEFAULT '',
    status_code INTEGER NOT NULL DEFAULT 0,
    duration_ms INTEGER NOT NULL DEFAULT 0,
    ip          TEXT    NOT NULL DEFAULT '',
    ua          TEXT    NOT NULL DEFAULT '',
    action      TEXT    NOT NULL DEFAULT '',      -- 业务动作名 auth.login / admin.user.ban
    target      TEXT    NOT NULL DEFAULT '',      -- 操作对象 user:12 / 项目 id
    payload     TEXT    NOT NULL DEFAULT '',      -- 脱敏后的参数 JSON
    result      TEXT    NOT NULL DEFAULT '',      -- ok / fail
    message     TEXT    NOT NULL DEFAULT '',      -- 失败原因 / 备注
    request_id  TEXT    NOT NULL DEFAULT ''       -- 同时回在响应头 X-Request-Id
);

CREATE INDEX IF NOT EXISTS idx_audit_created ON audit_logs(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_audit_user    ON audit_logs(user_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_audit_action  ON audit_logs(action, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_audit_route   ON audit_logs(route, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_audit_status  ON audit_logs(status_code, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_rt_user       ON refresh_tokens(user_id, expires_at DESC);
CREATE INDEX IF NOT EXISTS idx_rt_expires    ON refresh_tokens(expires_at);
```

### 字段设计的三条约定

1. **时间统一 UTC ISO 字符串**（`2026-11-04T10:00:00+00:00`）。字符串字典序正好等于时间序，`WHERE created_at >= ?` 直接走索引；前端用 `new Date(iso)` 转本地显示。混用本地时间会让跨时区统计全错。
2. **软状态用 TEXT + CHECK，不用 0/1**。日志和后台里直接能看懂 `banned`。
3. **外键都带 ON DELETE CASCADE**：删用户自动清掉他的令牌。

### 轻量迁移

`db._ensure_column()` 用 `PRAGMA table_info` 判断、缺列就 `ALTER TABLE ADD COLUMN`。以后加字段只需在 `db.init()` 里加一行，老库启动即升级（本项目没有改列类型/约束的场景，不需要 alembic）。

## 2. 接口清单

### 2.1 认证（`/api/auth`）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/auth/register` | 公开 | 注册。**第一个注册的用户自动成为 admin**；用户名 3-20 位（中文/字母/数字/`_`/`.`/`-`），密码 8-72 字节、不能纯数字 |
| POST | `/api/auth/login` | 公开 | 用户名**或邮箱**登录。返回 access + refresh + user |
| POST | `/api/auth/refresh` | 公开（凭 refresh） | 换新令牌对，**轮换**：旧的立刻作废 |
| POST | `/api/auth/logout` | 可登录 | 撤销当前 refresh；`all_devices=true` 则全部下线 + 版本号 +1 |
| GET | `/api/auth/me` | 可未登录 | 当前身份 + `auth_required` + 权限标记（前端据此决定显示不显示后台入口） |
| PUT | `/api/auth/profile` | 登录 | 改昵称 / 邮箱 / 头像 |
| PUT | `/api/auth/password` | 登录 | 改密码：校验旧密码 → 更新 → **所有旧 token 失效** → 给当前设备发新的一对 |

**登录响应**（注册 / 刷新 / 改密同构）：

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 7200,
  "refresh_token": "5f3a...（48 字节随机串）",
  "refresh_expires_in": 1209600,
  "user": {
    "id": 2, "username": "tester", "display_name": "测试员", "email": "",
    "role": "user", "status": "active", "must_change_pwd": 0,
    "last_login_at": "2026-11-04T10:14:15+00:00", "created_at": "..."
  }
}
```

**错误码约定**

| 码 | 场景 | 前端该怎么处理 |
|---|---|---|
| 400 | 参数/密码强度不合格 | 直接显示 detail |
| 401 | 用户名或密码不对 / 令牌失效 / 未登录 | 401 且带 token → 尝试刷新；刷新失败跳登录 |
| 403 | 账号已封禁 / 需要管理员权限 | 封禁：提示联系管理员；权限：提示无权限 |
| 409 | 用户名 / 邮箱已被占用 | 显示 detail |
| 429 | 连续 5 次密码错误被锁 10 分钟 | 显示 detail（含剩余分钟） |

> 安全细节：**「没这个人」和「密码不对」返回完全一样**（都是 401「用户名或密码不对」），避免被当成账号枚举接口。封禁判断放在密码校验**之后**，否则「封没封」也是信息泄露。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ai/grant` | 入参 `{project_id, purpose}`（purpose = `plan` / `shots`），返回 15 分钟票据 + 项目名 + 模型；**这一步顺带埋点，target 记 `project:剧名`** |

### 2.6 埋点的两种用法

**自动**：中间件对每个 `/api/*` 请求写一条，业务代码不用管。

**手动**（需要更准的动作名/失败原因时，加一行）：

```python
from . import audit

audit.log_event(me, "admin.user.ban", target=f"user:{uid}",
                payload={"reason": reason}, request=request)
# 失败时：
audit.log_event(user, "auth.login", result="fail",
                message="bad-password", request=request, status_code=401)
```

`log_event` **永不抛异常**（写日志失败绝不影响业务），并且在 `request.state` 上打一个
`audited` 标记 —— 中间件看到它就不再写第二条，避免同一个请求出现「一条有用户名、一条空用户名」的重复记录。

## 3. 后端代码

### 3.1 认证链路

```
POST /api/auth/login
   ├─ 查 user（username OR email，COLLATE NOCASE）
   ├─ locked_until > now ? → 429（不校验密码，也不泄露对错）
   ├─ bcrypt.checkpw 失败 → fail_count+1，满 5 次锁 10 分钟 → 401
   ├─ status != active → 403（提示封禁原因）
   └─ 成功 → 清零计数、记 last_login_at/ip
            → 签发 access(JWT, 120min) + refresh(随机串, 14d, 存 sha256)
```

**access token 的 payload**

```json
{"sub": 2, "uname": "tester", "role": "user", "tv": 3,
 "typ": "access", "iat": 1730000000, "nbf": 1730000000,
 "exp": 1730007200, "jti": "9f2c1a7b3d5e6f80"}
```

`tv` 就是 `users.token_version`。**这是封禁即时生效的关键**，比维护黑名单简单得多，也不依赖内存（重启后照样生效）。

**JWT 为什么自己实现 HS256**（`security.py`）：

- 标准 JWT 就是 `b64url(header).b64url(payload).b64url(HMAC-SHA256(...))`，40 行能写对且可审计；
- 不引 pyjwt / python-jose，PyInstaller 打包少一个变量，离线环境少一个装不上的风险；
- 三道检查缺一不可：结构必须三段、**`alg` 必须是 HS256**（不校验 alg 的实现能被 `{"alg":"none"}` 绕过，这是 JWT 最经典的历史漏洞）、签名用 `hmac.compare_digest` 比（避免时序侧信道）。

以后要换 RS256 / 接第三方签发，只改 `jwt_encode` / `jwt_decode` 两个函数，其余代码不动。

**refresh 为什么不用 JWT**：它需要**服务端可撤销**。JWT 一旦签出去就没法收回，而 refresh 有效期 14 天——账号被盗时你会需要一个「立刻让这个设备下线」的按钮。所以 refresh 是随机串，库里只存 sha256，支持撤销、轮换和查设备（IP/UA）。

**轮换（rotation）**：每次刷新都作废旧 refresh、发新的。好处不只是洁癖——refresh 泄露时，攻击者一刷新就会把用户的旧令牌挤掉，用户下次刷新会异常掉线，这个「异常掉线」本身就是泄露信号。实现上用 `UPDATE ... WHERE id=? AND revoked_at IS NULL` 的 `rowcount` 做原子判定，并发刷新只有一个能成功。

### 3.2 双重校验怎么落的

```
请求 → GuardMiddleware（audit.py）
        ├─ 非 /api/* → 直接放行（静态资源、页面）
        ├─ 取 token（Authorization: Bearer 或 GET 的 ?access_token=）
        ├─ 解析 + 查库 + 三重校验（存在 / status=active / tv 一致）
        ├─ ① 带了 token 但已失效 → 401/403
        ├─ ② 没带 token 且不在白名单 → 401
        ├─ 读 JSON body（≤8KB）→ 重放 → 下游照常能读
        └─ call_next → 写审计日志
     → 路由依赖（auth.py）
        ├─ current_user   = 必须登录（第二道，防中间件被绕过/顺序被改）
        └─ require_admin  = 必须管理员
```

**只有一种强度**：`auth.auth_required()` 恒返回 True（2026-11-04 用户定性）。
原先的「false = 只审计不拦截」已整体删除——它在多人/联网场景下会让封禁与踢下线失效。

**白名单**（不拦截）：`/api/auth/login`、`/api/auth/register`、`/api/auth/refresh`、`/api/status`、`/api/models-available`。前三个是「拿凭证的地方」，不能被旧凭证挡住。

### 3.3 封禁做了什么

`admin.ban_user()` 三件事，缺一不可：

```python
status = 'banned', ban_reason, banned_at, banned_by      -- ① 状态 + 留痕
token_version = token_version + 1                        -- ② 手里的 access 立刻作废
UPDATE refresh_tokens SET revoked_at=..., revoked_reason='banned'  -- ③ refresh 全部撤销
```

少了 ②③ 任意一条，被封的人都能继续用到 token 自然过期。
**解封也 +1**：封禁期间泄露的旧 token 不该因为解封就重新可用。

**第 ④ 件「顺手开登录墙」已成历史**：2026-11-04 用户报障「封禁了他还能用」，原因是
当时的免登录模式下，被封的人清掉本地凭证就变成匿名访问 → 200。修法当时是自动开墙，
现在登录墙**从启动就是立着的**（`auth_required()` 恒 True），所以 `_enforce_login_wall()`
恒返回 False，响应里的 `auth_required_enabled` 字段保留恒 False——前端不用改判断。

**被封用户看到的必须是 403 + 封禁理由，不是「登录已过期」**：`resolve_token` 里封禁判定
必须排在 `token_version` 比对之前——封禁时版本号也会 +1，先比版本号会把「被封」误报成
「过期」，用户以为只是掉线，重登又失败，一头雾水。

### 3.4 埋点与脱敏

中间件记录的字段：`method / path / route / query / status_code / duration_ms / ip / ua /
user_id / username / role / payload(脱敏) / result / request_id`。

**route 归一化**：中间件阶段路由还没匹配（匹配发生在 router 内部），所以用启发式——数字、12/24/32 位十六进制、UUID 段替换成 `{id}`。这样 `/api/projects/585dba7b8761/plan` 和 `/api/projects/779b3e51d3ae/plan` 才能归成同一行统计。

**脱敏三道闸**（`audit.mask()`）：

1. **键名命中就整值替换**：`password / passwd / pwd / secret / token / authorization / cookie / api_key / llm_key / ds_key / key / id_card / bank / card_no` → `"***"`；
2. **值处理**：邮箱 `a***@domain`、手机号 `138****45`、字符串截断 200 字；
3. **限深限量**：嵌套超过 3 层 → `"…"`，对象最多 30 个字段，数组最多 10 项，整体截断 2000 字符（防恶意深嵌套把日志表撑爆 / 卡住事件循环）。

**哪些请求不记**：`GET` 的两类——① 高频轮询（`/api/status`、`/api/projects/{id}` 每 1.5 秒一次、`/api/browse`、`/api/config` 等）；② **后台看板自己刷自己的查询**（`/api/auth/me`、`/api/admin/users`、`/api/admin/logs*`、`/api/admin/settings`，2026-11-04 补）。后者是用户报「日志没有记录」的另一半原因：管理后台每切一次 Tab 就是五连查询，全记下来第一页全是自己的刷新，真正的用户操作被挤出去。需要时可用 `request.state.force_audit = True` 强制记录。

### 3.5 登录节流

连续 5 次密码错 → 锁 10 分钟（`fail_count` / `locked_until` 落在用户表，不占内存，重启后继续有效）。锁定期间连密码都不校验，直接 429。

### 3.6 初始管理员

`auth.ensure_admin()`：`users` 表为空时创建 `admin`，密码取 `config.admin_init_password`（默认 `admin123456`），并标 `must_change_pwd=1`（前端登录后会一直提示改密）。

```
[auth] 已创建初始管理员：admin / admin123456（请登录后立即改密）
```

**上线前必须改掉这个默认值**（管理后台 → 系统设置，或直接改 `data/config.json`）。

### 3.7 服务端 AI Key 与调用票据（`app/aigate.py`）

**为什么要做**：用户明确要求「生成引流分镜 / 生成剪辑结构都由后端出 Key，不由用户自己填」。
Key 一旦进浏览器就等于公开（F12、插件、录屏都能读到），而这个项目的 AI 调用本来就发生在
后端（`analyze._call` / `shots.shots_run`）——前端需要的从来不是 Key，而是「这一步允许我调 AI」的许可。

```
前端  POST /api/ai/grant {project_id, purpose}
        ├─ 必须登录（current_user）
        ├─ 项目必须存在（core.load）
        ├─ 服务端凭证必须可用（配了 Key，或官方体验代理可连通）
        └─ 返回 { grant, expires_in: 900, project:{id,name}, model, provider, mode }
前端  带 X-AI-Grant 调 /plan 或 /shots
        └─ aigate.require() 验票通过才发 AI 请求
```

**票据里装什么**（JWT，HS256，复用 `security.jwt_encode`）：

| 字段 | 作用 |
|---|---|
| `sub` | 账号 id —— 换账号用不了 |
| `pid` | 项目 id —— 换项目就 403 |
| `purpose` | `plan` / `shots` —— 拿分镜的票排结构会 403 |
| `tv` | token_version —— 封禁/改密/踢下线后旧票立刻失效，不需要黑名单 |
| `exp` | 15 分钟 —— 够一次点击到任务启动，不够被人捡走长期刷 |

**为什么不直接把 Key 返给前端**：返了就等于永久泄露，且无法按人/按项目计量。
票据方案让「谁、在哪个项目、用什么模型、跑多久、成没成」全部进日志（见 §3.4 的
`ai.grant` / `plan.done` / `plan.fail` / `shots.done` / `shots.fail`）。

**后台可视化**：普通账号在「设置」里看不到 Key 输入框，只看到「AI 由服务端统一提供」；
管理员才看到「服务端 AI 凭证 · 百炼 / DeepSeek」两栏。`PUT /api/config` 按字段分权限——
模型与 Key 只有管理员能改，成片保存位置任何登录用户都能改。

## 4. 前端页面

> 本章只讲「有什么、怎么用、为什么这么写」。**逐字源码在 [`后台页面源码.md`](./后台页面源码.md)**——
> 那份文件由 `data/bench/gen_frontend_src.py` 从 `web/` 原文件直接生成，代码改了重跑脚本即可，
> 不会出现「文档里的代码和实际跑的不是同一份」。

### 4.1 三个页面

| 路径 | 文件 | 说明 |
|---|---|---|
| `/login` | `web/auth.html` | 登录 / 注册同卡切换（切 Tab 不跳页，不丢用户填的内容） |
| `/admin` | `web/admin.html` + `admin.js` | 管理后台：用户管理 / 操作日志 / 系统设置；支持 `#logs`、`#settings` 深链直达 |
| `/`（原有） | `web/index.html` | 右上角多了账号区（未登录显示「未登录」，管理员多一个「管理后台」入口） |

### 4.2 前端会话（`web/session.js`）

```js
Session.state.access / .refresh / .user   // localStorage 读写
Session.ureq(url, opts)                   // 带 Bearer，401 自动刷新一次再重试
Session.state.toLogin(next)               // 跳登录并记回跳地址
Session.logout(allDevices)                // 撤销 refresh + 清本地
```

**刷新单飞**：同一时刻只允许一个刷新在跑。服务端做了轮换，并发刷新会让后到的那次拿着已作废的 token 直接失败，用户会莫名其妙掉线——用 promise 缓存解决。

### 4.3 管理后台能做什么

- **用户管理**：搜索 / 角色筛选 / 状态筛选；表格里直接封禁（填理由）、解封、踢下线、改角色、重置密码；不能操作自己的那几个按钮会置灰并给出原因。
- **操作日志**：按用户 / 动作 / 方法 / 状态码 / 日期 / 关键字筛选；点任意一行展开脱敏后的参数（密码、Key 显示 `***`）；一键导出 CSV。
- **系统设置**：登录模式（固定启用，只展示）、令牌有效期、初始管理员密码。

### 4.4 主界面账号区

登录后右上角显示昵称 + 角色，点开菜单：管理后台（仅管理员）/ 修改密码 / 退出登录。
没有「未登录还能用」的状态了——本地没有凭证时 `boot()` 第一件事就是跳登录页。

### 4.5 什么情况下会被送回登录页（用户问的第 2 点）

**先分清两件事**：① 「进不去应用」= 被送回 `/login`；② 「进去了但这个动作不行」= 留在原地报错。
只有下面这些会**跳登录页**：

| # | 触发情况 | 后端返回 | 前端行为 / 登录页提示 |
|---|---|---|---|
| 1 | 打开应用但本地没有 access token（首次访问、清过缓存、换了浏览器） | —（`boot()` 直接判断） | 先试 refresh，失败则跳 `/login?next=/` |
| 2 | access 过期，且 refresh 也过期/被撤销 | 401 `code=unauthorized` | 跳登录页，提示「登录已过期，请重新登录」 |
| 3 | 管理员点了**封禁** | 403 `code=banned` | 清凭证 → 跳登录页，红字「账号已被封禁：＜理由＞」 |
| 4 | 管理员点了**踢下线** | 401 `code=revoked` | 清凭证 → 跳登录页，提示「账号已被要求重新登录」 |
| 5 | 自己（或管理员）**改了密码**（`token_version+1`，全部 refresh 撤销） | 401 `code=revoked` | 同上，需用新密码重登 |
| 6 | 管理员把角色从 admin 降为 user 后访问 `/admin` | 403（非 banned） | **不跳登录**，`/admin` 显示「需要管理员权限」 |
| 7 | 手动点「退出登录」 | — | 主动跳 `/login` |

**不会跳登录页、只是这个动作不行的**（重要，否则会误判成掉线）：

| 情况 | 返回 | 表现 |
|---|---|---|
| 普通用户改模型 / 改 Key | 403 | 设置页 toast「只有管理员能改…」 |
| 普通用户打开 `/admin` | 403 | 页面显示「需要管理员权限」+ 回工作台 |
| 生成时没带 AI 票据 / 票据过期 / 用途不对 / 换项目 | 403 | toast「AI 授权…请重新发起」 |
| 服务端没配 AI 凭证 | 409 | toast「服务端还没有可用的 AI 凭证…」 |
| 项目已有任务在跑 | 409 | toast「这个项目已有任务在跑」 |
| 登录密码错 5 次被锁 10 分钟 | 429 | 登录页提示「失败次数过多，稍后再试」 |

**服务端侧兜底**：即使前端被绕过（直接 curl），没带凭证访问任何 `/api/*`（白名单除外）
一律 401，日志里记 `auth.reject`，说明列写「未带凭证」「令牌已过期」「账号已被封禁」。

### 4.6 三道闸：需要更新时，更新完才能继续用（2026-11-04 新增）

用户要求「在需要更新的情况下，都需要更新之后才可继续使用」。落地成三道硬闸，
共同点是：**不弹窗提醒，直接把界面锁住**——提醒是可以无视的，锁屏不能。

**① 本地版本闸（`app/buildstamp.py` + `web/version.js`）**

防的是「后端已换新版，浏览器里还跑旧 app.js」——按钮点了没反应、参数按旧格式提交，
排查成本极高，而根因只有一句话：页面和服务器不是同一版。

```
buildstamp.current()  = web/ + app/ + prompts/ 全部文件的 (路径, 大小, mtime) 短哈希
   ├─ 页面路由注入 <meta name="app-build">，并把 /static/x.js 改成 ?v=<指纹>
   ├─ /api/status 回 build
   └─ 每个响应带 X-App-Build 头（页面开着不动，后端中途更新也能发现）
前端 version.js（三个页面最先加载）：
   比对 ①页面 meta ②status.build ③每个响应头 —— 任一对不上 → 全屏锁屏
   只有「立即刷新」一个按钮，没有「稍后再说」（稍后再说 = 又把旧页面放回去用）
```

配套缓存策略：HTML `Cache-Control: no-store`（页面永远现取），`/static/*` 强制回源校验。
指纹含 mtime，改完文件 2 秒内前端就能发现；顺序做了排序，不会「什么都没改也提示刷新」。
**局限**：exe 分发时用户电脑上的页面和后端来自同一份安装包，两者永远一致，
这道闸一次都不会触发——所以要配第③道。

**② 强制改密闸（`audit.py` 中间件第三道 + `session.js` 弹窗）**

还在用初始密码（`must_change_pwd=1`，管理员重置密码后同样置 1）的用户，
除了「读自己是谁 / 改密码 / 退出 / 续期」四个接口外**全部 403**：

```python
# audit.py GuardMiddleware，排在登录校验之后、业务之前
if user and user["must_change_pwd"] and path not in MUST_CHANGE_ALLOW:
    return JSONResponse({"detail": "你还在使用初始密码，请先修改密码再继续使用",
                         "code": "must-change-pwd"}, status_code=403)
```

前端 `Session.ureq()` / `api()` 收到这个 code 就弹一张**关不掉**的卡片
（原密码 / 新密码 / 确认），保存成功后整页重载——这就是登录后看到的第一个界面。
在中间件拦而不是只在前端提示，是因为前端可以被绕过（curl 直调照样要拦）。

**为什么初始密码要硬拦**：`ensure_admin()` 创建的 `admin/admin123456` 是写进文档的公开值，
等同于「谁都知道的钥匙」。以前只 toast 提示一句，等于没拦；现在改完密码这件事自动解除，
不需要任何额外操作。

**③ 远程版本闸（`app/update.py`，exe 分发必需）**

本地指纹闸管不了「这版程序本身不能用了」。判据必须来自机器外——服务器：

```
update.check()  →  GET {proxy_url}/api/version
                    服务端读 release.json（改文件即推更新，不用重启服务）
                    返回 {version, min_supported, url, note}
本地 min_supported > 本版  →  中间件返回 426 code=need-upgrade
                             除登录 / 探活 / 页面外一律拦死
前端收到 426 → 全屏「这个版本已停止使用」卡片，只有「下载新版」按钮，
               明确写清「刷新不起作用」
```

两条**宁可放过、不可误锁**的规则：
- 网络不通 / 接口没上线 → 视为最新，**不锁**（离线的人本来也用不了 AI，再锁在门外只会变成「软件坏了」的投诉）；
- 失败保留上一次成功的结果，10 分钟后重试，正常成功后 6 小时内不再问。

服务端对应文件：`deploy/proxy/app.py` 的 `GET /api/version` + `release.json.example`
（把 `min_supported` 改成最新版号就是推一次强制更新）。

### 5.2 配置项（`data/config.json`）

| 键 | 默认 | 说明 |
|---|---|---|
| `auth_required` | `true` | **恒为 true，改了也不生效**——登录模式是本版本的固定行为（`auth.auth_required()` 直接返回 True）。字段保留只为兼容旧配置文件 |
| `llm_key` / `ds_key` | `""` | **服务端 AI 凭证**，只在后端使用；配了就走自己的额度，没配走官方体验代理 |
| `jwt_secret` | 自动生成 | **不要手改**，改了等于全站登出 |
| `access_minutes` | `120` | access token 有效期 |
| `refresh_days` | `14` | refresh token 有效期 |
| `admin_init_password` | `""`（= admin123456） | 只影响「空库首次启动」创建的 admin |
| `dist_mode` | `false` | **分发版开关**，`build.bat` 打包时自动写入安装包的 config。开了之后：设置页不显示 Key / 模型 / 测试连通，后端拒绝改这些字段（`PUT /api/config` 403），Key 掩码也不回显 |
| `report_audit` | `""` | 日志上报开关：`""` = 跟随 `dist_mode`（开发机不推、分发版推），`true` / `false` 强制指定。详见 §5.6 |

### 5.6 exe 分发形态（给到用户的是安装包，不是网页）

**形态**：`钩子工坊.exe`（PyInstaller onedir）→ 本机 FastAPI → `127.0.0.1:8100` →
用户浏览器打开的确实是网页，但**服务和数据都在用户自己的电脑上**。
这带来四件必须做的事（2026-11-04 复查后已全部落地）：

1. **AI 请求谁发** —— 由用户本机的后端发，不经过你的服务器（自备 Key 时），
   或只经你的代理转发（体验额度时）。不存在「服务器替所有用户跑 AI」的压力问题；
   也因此**不能让浏览器直接拿 Key 调百炼**：违背「Key 不进浏览器」，百炼也不允许浏览器跨域。
2. **Key 从哪来** —— 安装包里的 `data/config.json` 只有 `{"dist_mode": true, "report_audit": true}`
   两个开关，**没有任何 Key**。没 Key 时自动走官方体验代理（`proxy_url` +
   设备令牌，额度记在服务端）；终端用户全程不需要、也填不了 Key（接口层 403 兜住）。
3. **版本闸靠谁判** —— 本地指纹闸在 exe 上永远不触发，见 §4.6 第③道远程闸。
4. **埋点日志在哪** —— 写在用户本机 `data/app.db`，后台看板看的是**本机**库；
   分发后要看到用户的操作，靠 `app/report.py` 每 60 秒把增量推到
   `{proxy_url}/api/audit/ingest`（失败重试、断网不丢、`UNIQUE(device, request_id)` 去重）。
   服务端用 `/admin/logs?limit=50`（带 `X-Admin-Key`）查看，`/admin/stats` 里也能看到设备数。

**打包注意（`build.bat` 已内置）**：

- 打包自动写分发配置，**绝不拷贝开发机的 `data/config.json`**（里面有明文 Key）；
  打包前还会做一道防呆提醒；
- `--noupx`：UPX 压缩 onnxruntime / ctranslate2 的 `.pyd` 有已知崩溃案例
  （转写一跑就 0xC0000005），省几十 MB 不值得；
- onedir 而不是 onefile；只带 small 模型；`data` 目录保持为空。

**必须想清楚的边界**：exe 在用户手里，本机的 `data/`、`app.db` 用户都能删改，
登录/埋点在本机只是**界面层**的约束；真正的额度与授权控制在服务端（代理按设备令牌
计数 + 版本闸 + 日志上报）。别把「本机后台封禁」当成对终端用户的强制力。

也可以用环境变量覆盖（优先级更高）：`HOOKSTUDIO_AUTH=1` 这种形式的开关目前没做，统一走 config / 管理后台。

### 5.7 免费额度的规则：每天 10 次（2026-11-04 改，勿改回「总共 10 次」）

用户口径：**普通用户每天只能调用 API 10 次**。落地成「按天重置」，不是「一辈子 10 次」——
后者用户试完 10 次就永久废了，前者第二天还能回来，对新工具更合理。

**计费口径**

| 情况 | 算不算 1 次 |
|---|---|
| AI 调用成功返回 200 | ✅ 算 |
| 上游报错（400/402/429/5xx） | ❌ 不算（`_bump_today` 只在 `ok` 时执行） |
| 转写、切片、出片、分镜渲染 | ❌ 不算（纯本地） |
| 自己填了百炼 Key | ❌ 不走代理，不占额度 |

**按北京时间切天**：服务器在境外，用 UTC 切会让用户在晚上 8 点就"跨天"。所以
`_day_key()` 统一加 `DAY_TZ_OFFSET = 8h`，配额在**北京时间 0 点**回满。

**存储**：`daily_usage(token, day, calls, bonus)`，主键 `(token, day)`。
`tokens.remaining` 列已停用（历史上是"一辈子 10 次"），保留只为兼容旧库，别再去读它。

**接口**：`GET /api/quota` 现在回

```json
{"remaining": 9, "total": 10, "used": 1, "scope": "day",
 "day": "2026-11-04", "reset_in": 13125}
```

`scope=day` 是给前端的信号：文案必须写「**今天**还剩 N 次」，不能只写「还剩 N 次」，
否则用户会当成永久额度。前端 `web/app.js` 的 `#trial-hint` 已按这个口径改写。

**用完之后**：`POST /api/proxy/chat/completions` 返回 **402**，
文案「今天的免费次数已用完（每天 10 次，明天自动恢复）；也可以在设置里填自己的百炼 Key 继续用」。
注意 402（额度用完）和 429（网络级限流）必须分开提示——客户端的 `analyze._call`
已经分成两条不同的报错，别合成一条。

**临时加量**：`POST /admin/grant {"token": "...", "add": 5}` 只补**当天**
（写进 `daily_usage.bonus`），跨天自动清零。以前那套「给某个 token 加一辈子额度」
在按天计费下没有意义，已删除。

**改阈值**：`.env` 里 `FREE_CALLS_PER_DAY=10`，改完 `systemctl restart hsproxy` 生效，不用重新部署。

**反刷边界**：设备令牌是客户端自己生成的，随便新造一个就是新的 10 次/天，
所以「每天 10 次」挡的是正常用户的手滑，不是刷子。刷子靠
`IP_LIMIT_HOUR` / `IP_LIMIT_DAY` 兜（默认 30/200，也在 `.env` 里）。
真要收紧，下一步是「同一 IP 每天最多新建 N 个令牌」——目前没做。

**验证**：`runtime/Scripts/python.exe data/bench/test_quota_daily.py`（19 项，无需联网、
不烧额度；靠 monkeypatch `_day_key` 把时钟拨到明天来验证跨天回满）。

### 5.3 部署到公网 / 多人使用的必做清单

- [ ] 改掉 `admin_init_password`，或登录后立刻改 admin 的密码
- [x] 登录模式（本版本固定启用，不需要手动打开）
- [ ] 用 Nginx / Caddy 反代并配 HTTPS（JWT 在 HTTP 上等于明文密码）
- [x] 反代要透传真实 IP（2026-11-04 已内置且实测）：代理服务读 `X-Forwarded-For` 第一段。
  **不加这一步的后果不是"IP 不准"这么轻**：对端恒为 127.0.0.1，`IP_LIMIT_HOUR` 会从
  「每 IP 每小时 N 次」退化成「**全网合计每小时 N 次**」，第 N+1 个用户直接 429。
  已用伪造 XFF 实测：caddy 会覆盖客户端伪造值，取第一段是安全的。
- [ ] `data/app.db` 和 `data/config.json` 加入备份；`app.db` 里有密码哈希，别放到公开目录
- [ ] 定期清理日志：`DELETE FROM audit_logs WHERE created_at < date('now','-90 day');`（或加个定时任务）

### 5.4 常见问题

**Q：封禁 / 踢下线了，怎么那个人还能用？**
A：这个 bug 的根子是「免登录模式」——业务接口不要求身份，任何人清掉本地凭证就是匿名访问。
2026-11-04 起该模式已整体删除（`auth.auth_required()` 恒 True），所以不存在这个问题了。
现在封禁 = 状态置 banned + `token_version+1` + 撤销全部 refresh，三条一起做，旧凭证立刻失效。

**Q：封禁后用户那边看到什么？**
A：立即弹回登录页，红字提示「账号已被管理员封禁，无法继续使用」，再登录时提示
「账号已被封禁：＜理由＞」。不会看到笼统的「登录已过期」——`resolve_token` 的封禁判定
排在版本号比对之前，这是 2026-11-04 修的。

**Q：日志里看不到某用户的操作？**
A：按顺序查三件事：① 那行「用户」列显示「匿名」→ 请求没带凭证（现在只有白名单接口能匿名）；
② 该用户确实登录了但看不到 → 日志页按「用户」筛一下；③ 都不是 → 看是不是路由进了
`_worth_logging_get` 的排除名单（轮询和看板自查询故意不入库）。

**Q：忘记 admin 密码了？**
A：本机工具没做邮件找回。两个办法：① 另一个管理员登录后重置；② 停服务，删 `data/app.db` 里的 admin 行（或整个库），重启会重建初始管理员（**代价是日志和账号一起没了**）。更稳的做法是提前再建一个管理员账号。

**Q：自己进不去了？**
A：初始管理员一定存在（空库时自动创建）。如果库被改过，直接停服务删 `data/app.db` 重启。

**Q：为什么设置里看不到填 Key 的地方？**
A：Key 归服务端（`data/config.json`），普通账号看不到也不该看到。管理员登录后才出现
「服务端 AI 凭证」两栏；生成分镜/结构时前端只申领一次性票据，Key 不会进浏览器。
换 Key 请在管理后台改，或直接编辑 `data/config.json` 的 `llm_key` / `ds_key`。

**Q：日志表涨得太快？**
A：默认已经排除了高频轮询。还能再压：把 `_worth_logging_get` 的白名单扩大，或按 5.3 最后一条定期清理。

**Q：`<video src>` 播不了（401）？**
A：`<video>` / `<img>` 没法带请求头，所以 `token_from_headers` 支持 GET 的 `?access_token=xxx`。视频预览接口就是这么用的；**只对 GET 生效**，其他方法一律要 Authorization 头。

**Q：改了密码，别的设备还在线？**
A：不会。改密码会把 `token_version + 1` 并撤销该用户全部 refresh，所有旧 token 立即失效，只有发起改密的这台设备拿到新的一对。

### 5.5 扩展点

- **加字段**：`db.init()` 里加一行 `_ensure_column(...)`，重启即升级。
- **加权限**：现在只有 `user` / `admin`。要更细的（比如「只能看日志不能封人」），在 `users` 加 `perm` 字段并在 `auth.require_admin` 旁边加一个 `require_perm("audit")` 依赖。
- **接第三方登录**：`auth.login` 里签发逻辑抽成了 `_issue()`，微信/GitHub 回调拿到身份后直接调 `_issue()` 即可。
- **日志进 ELK / 外部存储**：`audit.log_event()` 是唯一写入口，在里面加一个异步 sink 就行。
